# Тест-кейсы API qa-internship

## Общие правила

- Базовый URL: `https://qa-internship.avito.com`.
- Для каждого независимого сценария создаются уникальные username и данные объявления.
- Все защищённые запросы выполняются с токеном, полученным через `/api/1/autorize`.
- Если тест создал объявление, после теста выполняется попытка его удаления.
- В ожидаемых результатах JSON должен иметь `Content-Type`, содержащий `application/json`.
- Сервис не должен возвращать `5xx` на некорректные пользовательские данные.
- Поля с неописанными в контракте ограничениями проверяются методом классов эквивалентности и анализа обязательности.
- UUID объявления извлекается из строки `status` ответа создания.

## Использованные техники тест-дизайна

- классы эквивалентности: корректные и некорректные учётные данные;
- анализ граничных значений: пустое имя и отрицательная цена;
- таблица решений: отсутствующий, некорректный и корректный Bearer-токен;
- переходы состояний: объявление создано → доступно → удалено → недоступно;
- error guessing: подмена `sellerID`, `X-UserId`, неверные типы JSON;
- pairwise на уровне обязательных полей запросов;
- security testing: Broken Authentication и IDOR/BOLA;
- нефункциональная проверка времени ответа.

## Регистрация и авторизация

### AUTH-001 — Успешная регистрация уникального пользователя

**Приоритет:** критический  
**Тип:** позитивный, функциональный

**Предусловия:**

- Сервис доступен.
- Сгенерирован уникальный username.

**Шаги:**

1. Отправить `POST /api/1/register` с уникальными `username` и `password`.

**Ожидаемый результат:**

- HTTP 201.
- Ответ в JSON.
- `id` является положительным числом.
- `username` совпадает с отправленным.

**Автоматизация:** `RegistrationAuthorizationTest.registersUniqueUser`.

### AUTH-002 — Успешная авторизация зарегистрированного пользователя

**Приоритет:** критический  
**Тип:** позитивный, функциональный

**Предусловия:**

- Зарегистрирован уникальный пользователь.

**Шаги:**

1. Отправить `POST /api/1/autorize` с корректными username и password.

**Ожидаемый результат:**

- HTTP 200.
- `accessToken` существует и не пуст.
- `tokenType` равен `Bearer` без учёта регистра.

**Автоматизация:** `RegistrationAuthorizationTest.authorizesRegisteredUser`.

### AUTH-003 — Повторная регистрация username

**Приоритет:** высокий  
**Тип:** негативный, класс эквивалентности

**Предусловия:**

- Пользователь уже зарегистрирован.

**Шаги:**

1. Повторно отправить регистрацию с тем же username и password.

**Ожидаемый результат:**

- HTTP 409.
- Новый пользователь не создаётся.

**Автоматизация:** `RegistrationAuthorizationTest.rejectsDuplicateUsername`.

### AUTH-004 — Регистрация без обязательного username

**Приоритет:** высокий  
**Тип:** негативный, проверка обязательного поля

**Предусловия:** отсутствуют.

**Шаги:**

**Ожидаемый результат:**

- HTTP 400.

**Автоматизация:** `RegistrationAuthorizationTest.rejectsRegistrationWithoutUsername`.

### AUTH-005 — Авторизация с неверным паролем

**Приоритет:** критический

**Предусловия:**

- Зарегистрирован пользователь.

### AUTH-006 — Авторизация с неполным телом

**Приоритет:** высокий

## Контроль доступа

### ACCESS-001 — Защищённые ручки без Bearer-токена

**Приоритет:** критический  
**Тип:** негативный, таблица решений, security

**Предусловия:** отсутствуют.

**Шаги:**

1. Поочерёдно обратиться без Authorization к:
   - `POST /api/1/item`;
   - `GET /api/1/item/{id}`;
   - `GET /api/1/{sellerID}/item`;
   - `GET /api/1/statistic/{id}`;
   - `GET /api/2/statistic/{id}`;
   - `DELETE /api/2/item/{id}`.

**Ожидаемый результат:**

- Каждая ручка возвращает HTTP 401.
- Операция не выполняется.

**Автоматизация:** `AccessControlTest.protectedEndpointRejectsRequestWithoutToken`.

### ACCESS-002 — Защищённая ручка с некорректным токеном

**Приоритет:** критический  
**Тип:** негативный, security

**Предусловия:** отсутствуют.

**Шаги:**

1. Запросить объявление с синтаксически некорректным Bearer-токеном.

**Ожидаемый результат:**

- HTTP 401.
- Данные не возвращаются.

**Автоматизация:** `AccessControlTest.protectedEndpointRejectsMalformedToken`.

### ACCESS-003 — Нельзя создать объявление от имени другого пользователя

**Приоритет:** блокирующий  
**Тип:** негативный, BOLA/IDOR

**Предусловия:**

- Зарегистрированы и авторизованы пользователи A и B.

**Шаги:**

1. С токеном A отправить создание объявления, указав `sellerID` пользователя B.
2. Добавить `X-UserId` со значением B.

**Ожидаемый результат:**

- HTTP 400.
- Объявление для B не создаётся.
- `X-UserId` не переопределяет пользователя из JWT.

**Автоматизация:** `ItemApiTest.rejectsSellerIdSubstitutionAndIgnoresXUserId`.

### ACCESS-004 — Другой пользователь не может удалить чужое объявление

**Приоритет:** блокирующий  
**Тип:** негативный, BOLA/IDOR

**Предусловия:**

- Пользователь A создал объявление.
- Пользователь B авторизован.

**Шаги:**

1. Пользователем B удалить объявление A.
2. Пользователем A запросить объявление.

**Ожидаемый результат:**

- Удаление возвращает 401 или 404.
- Существование защищённого ресурса может быть скрыто через 404.
- Объявление остаётся доступным владельцу.

**Автоматизация:** `ItemApiTest.otherUserCannotDeleteAdvertisement`.

## Объявления

### ITEM-001 — Создание и чтение объявления

**Приоритет:** критический  
**Тип:** позитивный, функциональный

**Предусловия:**

- Зарегистрирован и авторизован уникальный пользователь.

**Шаги:**

1. Создать объявление со своим sellerID.
2. Извлечь UUID из `status`.
3. Получить объявление по UUID.

**Ожидаемый результат:**

- Создание возвращает HTTP 200.
- В `status` содержится валидный UUID.
- Чтение возвращает HTTP 200 и массив из одного элемента.
- UUID, name, price и sellerID соответствуют созданному объявлению.

**Автоматизация:** `ItemApiTest.createsAndReadsAdvertisement`.

## E2E и нефункциональные проверки

### E2E-001 — Полный жизненный цикл объявления

**Приоритет:** блокирующий  
**Тип:** сквозной, переход состояний

**Предусловия:**

- Сервис доступен.

**Шаги:**

1. Зарегистрировать уникального пользователя.
2. Авторизовать пользователя.
3. Создать объявление.
4. Получить объявление по UUID.
5. Получить объявления продавца.
6. Получить статистику v1.
7. Получить статистику v2.
8. Удалить объявление.
9. Повторно получить объявление.

**Ожидаемый результат:**

- Регистрация — 201.
- Авторизация — 200 и Bearer-токен.
- Создание — 200 и UUID.
- Все чтения до удаления — 200 и согласованные данные.
- Удаление — 200.
- Чтение после удаления — 404.

**Автоматизация:** `E2eTest.userCanCompleteFullAdvertisementLifecycle`.

### NFR-001 — Время ответа публичной ручки

**Приоритет:** средний  
**Тип:** нефункциональный, performance smoke

**Предусловия:**

- Задано допустимое время `performanceMaxMs`, по умолчанию 5000 мс.

**Шаги:**

1. Зарегистрировать уникального пользователя.
2. Измерить полное время ответа.

**Ожидаемый результат:**

- HTTP 201.
- Время не превышает настроенный предел.

**Примечание:**

Это smoke-проверка, а не нагрузочный тест. При падении на общем стенде результат необходимо подтвердить повторными измерениями.

**Автоматизация:** `RegistrationAuthorizationTest.registrationRespondsWithinConfiguredLimit`.
